构建关键点(顶层 CMakeLists.txt):

  • minirtos 必须 --whole-archive,否则 SDK 的 weak isr_pendsv 会抢占 vector table
  • drivelib / uigeom / appmgr 之间存在循环引用(app_led.o 引用 ui_switch_set_state,而 libuigeom.a 在 libappmgr.a 之前处理),用 --start-group / --end-group 让链接器反复扫描直到收敛
  • USB CDC stdout 1ms 超时(PICO_STDIO_USB_STDOUT_TIMEOUT_US=1000):host 未开串口监视器时不会卡 RTOS 任务

🔴 严重问题(4 项)

严重架构
app_manager ↔ app 通过 user_data 强耦合的脏矩形契约,运行时可崩溃
app/app_manager.c:230, 249 · app/app_led.c:10

app_manager_process_touch_dirty 在分发触控给当前 App 后,直接做强制类型转换取脏矩形:

*out_dirty = *(ui_rect_t *)cur->user_data;

这个写法假设 每个 app 都把自己 user_data 的第一个字段定义为 ui_rect_t dirty_rect。app_led.c 第 10 行的注释 // 必须放在第 1 位，供 app_manager 提取局部脏矩形 正是这种隐式契约的体现。

风险:

  • 任何新 App(app_uart / app_scope / app_dap ...)如果忘了把 dirty_rect 放第一个字段,或者根本没用 user_data,代码会读取 ui_rect_t* 错误解释的内存 → 渲染脏矩形乱跳,严重时画到屏外 / 越界
  • App 返回 true 时 out_dirty 已被赋值,但 app_manager 不会校验其合法性(如是否在屏幕内、宽高是否 > 0)
  • app_led 在 sw_state 改变时只标了 ui_switch_get_dirty_rect + 紧邻的状态指示区(30,80,300,32),但 ui_switch_get_dirty_rect 内部行为若改为包含动画过渡(rect.w > 64),局部矩形会外溢

建议修复方向:

  1. 扩展 app_t 接口,加 get_dirty_rect(app_t *) 回调,让 App 显式提供自己的脏矩形
  2. 或者让 App 的 process_touch 返回 out_dirty 通过参数(bool process_touch(app_t*, is_touching, tx, ty, now_tick, ui_rect_t *out_dirty))
  3. 在 app_manager 中加 ui_rect_intersect 把脏矩形裁剪到 LCD 视口,防止越界
严重正确性
ui_switch_get_dirty_rect 是否存在?链接与运行时一致性未验证
app/app_led.c:71 · app/app_led.c:118

app_led.c 调用了 ui_switch_get_dirty_rect 和 ui_switch_set_state,但只验证过 ui_switch_set_state 通过 --start-group 链接进来了。ui_switch_get_dirty_rect 是否真的在 ui_switch.c 中实现,本轮审查未独立确认。

如果 ui_switch.h 只声明了 get_dirty_rect 而 .c 漏写,链接会在下一次清理 / 重排时炸(当前 --start-group 的副作用是 不调用就不报错,只调用了才报)。

建议:

  • 在 ui_switch.h 与 ui_switch.c 中 grep 验证 get_dirty_rect 与 set_state 同时存在
  • 对所有控件统一加静态断言:每个控件的 _get_dirty_rect 必须返回自己 rect 的有界裁剪
严重正确性
ui_drawer.c 滚动列表的 rel_y 计算存在整数下溢风险
ui/ui_drawer.c:152-153

抽屉列表项点击命中检测中:

int16_t rel_y = (int16_t)(ty - sv_body.view_rect.y + scroll_y);

当用户向上滚动(scroll_y 持续增大)且手指落在 view_rect 上方(ty < view_rect.y),或 scroll_y 大于 ty - view_rect.y 时,计算结果为负。rel_y 是 int16_t,后续 rel_y / item_height 用作数组下标会读到错误的项。

触发场景: 抽屉内有 10 个 App,内容超过可视区,用户已经滚到列表底部并尝试再次向上滑动,会进入 rel_y < 0 分支。

建议:

int16_t rel_y = ty - sv_body.view_rect.y;
if (rel_y < 0) return false;           // 视口外直接返回
rel_y += scroll_y;
if (rel_y < 0) return false;           // 滚动过头也直接返回
int idx = rel_y / item_height;
if (idx < 0 || idx >= app_count) return false;
严重架构
ui_drawer.h 包含 app_base.h 形成跨层依赖,易触发循环依赖
ui/ui_drawer.h:8

现状依赖链:app/app_base.h 包含 ui_tile.h / ui_geometry.h,而 ui_drawer.h 反向包含 app_base.h。这意味着任何使用 ui_drawer.h 的 UI 模块都必须先有完整的 app_t 类型,而 ui/ 本身设计为 不依赖 app/ 的底层渲染层。

如果以后给 app/ 加更复杂的头文件(比如 app_manager.h 被 app_base.h 间接拉进来),就会形成 app → ui → app 的循环 include。

建议:

  • 将 app_t 类型前向声明到 ui_drawer.h,只在使用 app_t* 字段时 include app_base.h
  • 或者把抽屉拆为 ui_drawer.h(纯 UI,只管 on_select(idx, user_data) 回调)+ app_drawer_bridge.h(桥接 app_manager 与 ui_drawer)

🟠 重要问题(8 项)

重要正确性
app_manager 的边缘手势状态机:松手逻辑缺失
app/app_manager.c:236-254

在触控抬起分支(is_touching == false):

mgr->edge_touch_down  = false;
mgr->edge_candidate   = 0;
bool was_consumed     = mgr->gesture_consumed;
mgr->gesture_consumed = false;
if (was_consumed) return false;

如果在 按下后 但 未达到阈值 时,用户抬起手指,本分支会把 gesture_consumed 清掉后继续往下走分发,看起来是对的。但 edge_touch_down 复位后,下一次按下时 edge_down_x / edge_down_y 才被重新捕获,逻辑上没问题。

但有一个真实问题:在抽屉 打开状态 时(第 165 行),如果用户做了一个未触达抽屉矩形(tx > 140)的边缘滑动,ui_drawer_process_touch 会按"外部点击"判定为 关闭抽屉,返回 true + *out_dirty = drawer.rect + *is_full_frame = true(因为抽屉关闭后要全刷)。但此时用户手指还在屏上,后续滑动会被 app_manager_process_touch_dirty 的"抽屉已关闭"分支重新认作边缘手势,左滑会再次触发 return_home。

建议: 抽屉关闭与手势消费应该是同一个事件,在抽屉关闭后,直到 edge_touch_down 真正松手(is_touching == false)再清 gesture_consumed。

重要架构
app_t 的 user_data 同时承担"实例数据"和"脏矩形传输"两种语义
app/app_base.h · app/app_manager.c

app_t::user_data 一开始设计是"实例私有数据"(任何类型都可以),现在被 app_manager 强制当作 ui_rect_t * 来读。两种语义混在一起导致:

  • 任何 App 想存复杂状态(链表 / 缓冲区 / 多个字段),都要 把 dirty_rect 放第一个字段
  • 如果 App 内部还有别的控件(如 ui_switch + ui_btn),它们的脏矩形需要 App 自己 union,如 app_led.c:73
  • 对不需脏矩形的 App(纯显示型)会被强制要求实现 dirty_rect 字段,污染业务代码

建议: 与 C1 的修复合并:把 user_data 拆为两个明确字段 dirty_rect + user_data,或让 App 通过 process_touch 的 out 参数返回脏矩形。

重要性能
ui_waveform 每像素独立 for 循环,长波形帧率受限
ui/ui_waveform.c:248-267, 281-293

数字通道与模拟通道的绘制都是 for (px = start_x; px < end_x; px++) 单像素循环:

  • 数字模式:每个像素 1 次 s_idx 计算 + 1 次 mask 查表 + 可能 2 次 ui_draw_point/vline
  • 模拟模式:每个像素 1 次 ui_draw_line(含 1 次 Bresenham + 大量像素写)

在 320×240 视口 8 通道数字模式下,单切片可能跑 ~4000 次循环 + ~8000 次绘制调用,单帧 15 个切片累加起来接近 6 万次绘制调用。在 Cortex-M0+ 上跑满 60 FPS 几乎不可能。

建议:

  • 对数字模式做 行缓冲(level run):扫描出连续的高电平/低电平段,用 ui_draw_fast_hline 一次画完,只对跃变点画 vline
  • 对模拟模式做 降采样 + 折线段批绘:samples_per_pixel > 1 时整段取 min/max/avg,跳过绘制几乎平的段
  • 复用 ui_draw_set_clip 区间:先遍历求出与 tile 的 X 裁剪范围再进入循环
重要正确性
ui_waveform.cursor_a/b_x 在初始化时未对齐到采样边界
ui/ui_waveform.c:40-41
wf->cursor_a_x = x + w / 4;
wf->cursor_b_x = x + (w * 3) / 4;

这两个游标的 X 坐标直接当屏幕像素用,但在 format_time_delta 中却是用 (cursor_a_x - draw_start_x) * samples_per_pixel 反推采样点数。问题是:

  • 如果游标 A 与游标 B 距离 小于一个像素的样本数(如 samples_per_pixel = 4),用户看到的两个游标之间差了 100px,但真实只覆盖 400 个采样点,测量精度与视觉对不上
  • 如果游标 A 落在 draw_start_x 左侧(因为游标可拖到 rect.x),ca = 0,但视觉上它并不在 0 点

建议: 游标坐标应以 采样索引 而非像素存储(cursor_a_sample),渲染时再换算到像素:px = draw_start_x + cursor_a_sample / samples_per_pixel。

重要正确性
ui_waveform_set_scale 对 samples_per_pixel = 0 的兜底只处理一次
ui/ui_waveform.c:78
wf->samples_per_pixel = (samples_per_pixel > 0) ? samples_per_pixel : 1;

当 samples_per_pixel = 0 时会被替换为 1,但下游 ui_waveform_draw 中:

uint32_t s_idx = wf->view_offset + (uint32_t)(px - draw_start_x) * wf->samples_per_pixel;
if (s_idx >= wf->total_samples) break;

如果 total_samples < rect.w * samples_per_pixel,view_offset 会被夹紧到 0,但 s_idx 仍会超出 total_samples。break 后那一行的 右半部分会保留上一帧的像素,造成"残影"。

建议: 在 ui_waveform_draw 进入主循环前,先 ui_draw_fill_rect(tile, &overlap, wf->color_bg)(已经做了),但循环结束后若 px < end_x 也应 fill 剩余区域。或者修改 break 改为 continue 但用 color_bg 绘制 ui_draw_point。

重要架构
app_manager_draw 在 home 与 App 之间硬切换,无淡入淡出/状态保存
app/app_manager.c:259-272

每次 app_manager_draw 都直接 if (mgr->is_home) draw_home_dashboard(...) else cur->draw(...),这意味着切换 App 时:

  • 整个 home dashboard 会被无差别画一遍,即使它根本不在当前脏矩形内(draw_home_dashboard 自己也做 intersect 裁剪,问题不大,但有冗余字符串绘制开销)
  • 无 on_pause / on_resume 概念:从示波器切到 GPIO,示波器的 DMA 缓冲不会被通知暂停,可能在切换瞬间丢帧
  • 无应用栈:只能有"一个 home + 多个一级 App",无法支持 App 嵌套(如"设置" → "WiFi 配置")

建议: 给 app_t 加 pause / resume 钩子;为多层级 App 引入 app_manager_push / app_manager_pop 栈结构。

重要可移植
ui_drawer.c 用硬编码 (140) 判断 "点击抽屉外"
ui/ui_drawer.c:115
if (tx > d->rect.w) {  // 抽屉外点击关闭

这里 tx > d->rect.w 等价于 tx > 140(因为 d->rect.x = 0),这只是因为当前布局下抽屉从屏幕左边缘起。如果以后抽屉从右边缘起(rect.x = 340,rect.w = 140),这个判断就会失败。

建议: 改为 !ui_rect_contains_point(&d->rect, tx, ty),与 UI 几何语义对齐。

重要正确性
app_led_process_touch 在 on/off 状态切换时未重绘状态文字
app/app_led.c:77-81

当用户点 翻转按钮 时,流程是:

on_btn_toggle_click -> data->sw_state = !data->sw_state;
                   -> ui_switch_set_state(&data->sw_led, data->sw_state);

但是 app_led_process_touch 在 btn_changed 分支只把 data->dirty_rect = data->btn_toggle.rect(130,218,220,44),即按钮自身矩形。

问题: 状态指示区(20,50,440,76)中显示的"状态: 开启/关闭"文字由 sw_state 决定,翻转按钮会改变 sw_state,但 dirty_rect 不包含状态卡区域 → 文字不刷新,屏幕残留旧文字。

建议: 翻转按钮的脏矩形应包含 ui_switch_get_dirty_rect + status_card 三个区域的并集。

🟢 性能优化(6 项)

性能
ui_waveform_draw 中 ui_draw_set_clip 在 15 个切片上重复调用
ui/ui_waveform.c:204, 331

每个切片都进入 ui_waveform_draw,然后 ui_draw_set_clip(&wf->rect) 整 15 次。再 ui_draw_reset_clip 15 次。ui_draw_set_clip 即使内部只是写一个全局变量,这 30 次调用本身不是热点,但可以在调用方做"一次性裁剪累加":让 ui_tile_t 自带 clip 状态,只在切片开始时设一次。

建议: 把 clip 状态合并到 ui_tile_t 结构体,或让 ui_waveform_draw 检查 tile->rect 是否完全包含 wf->rect,只在部分相交时设置 clip。

性能
draw_home_dashboard 每次都重复绘制字符串,缺乏缓存
app/app_manager.c:19-74

home dashboard 是常驻界面,但每次 app_manager_draw 都重新画所有字符串和图标。RP2040 的 LCD SPI 推流是带宽密集型操作,每次刷新 480x320 全屏就需要 ~300 KB SPI 流量(16 bpp)。

建议:

  • 在 app_manager 中加 home_dirty 标志:仅在 home 第一次进入 / 状态变化时全刷,否则用脏矩形
  • 把 home dashboard 拆为可独立标脏的子区域(顶部横幅 / 监视看板 / 手势说明),用 ui_tile 切片
  • 或预渲染 home 到一块 framebuffer,只重画有更新的部分
性能
RTOS 任务栈溢出保护缺失
rtos/OS_Core/os_core.c · 任务调度

MiniRTOS 没有 stack canary 检测机制。一旦某个任务(如 display_task)因 ui_label_set_text 触发重渲染循环而爆栈,会无声地覆盖相邻任务的栈空间。最近一次 hang 事故正是这个原因。

建议:

  • 在 os_task_create 时在栈底填充 0xDEADBEEF / 0xCCCCCCCC 哨兵值,idle task 每隔 N 毫秒扫描所有任务的栈底,发现被覆盖则 printf 报警 + 软复位
  • 或者在 PendSV 上下文切换时检查 SP 是否越过栈底
性能
snprintf + ui_draw_string 反复构造时间字符串
ui/ui_waveform.c:176-189

每次 ui_waveform_draw 都用 snprintf 重新生成 time_str(双精度浮点除法、乘 1e9/1e6/1e3)。在游标拖拽场景下,每帧都要算一次,而字符串内容常常没变。

建议:

  • 在 ui_waveform_t 缓存 char last_time_str[32] 与 last_delta_samples,仅在 delta_samples 变化时重算
  • 用整数算术替代浮点:ns = delta_samples * 1000000000ULL / sample_rate,分支判断用 if (ns < 1000) ...
性能
chinese.c 的 GB2312 查表未做 O(1) 优化
Drivers/chinese.c

GB2312 一级汉字 3755 个、二级 6763 个,共 ~1 万字。当前如果用顺序查表,每次显示一个汉字都是 O(N)。如果用 Unicode → GB2312 区位码的映射表,内存约 2 万个 uint16_t(~40 KB),可以做到 O(1)。

对嵌入式来说 40 KB 不算小,但可以拆为常用 500 字小表 + 大表两段。

建议: 评估实际使用的汉字集合,只缓存出现频率高的;或接受 40 KB 换取 O(1)。

性能
SPI 推流未启用 DMA 双缓冲
Drivers/lcd.c · pico.cpp

当前 LCD 推流是 CPU 直接写 SPI FIFO,在 320x480 全屏刷新时 CPU 占用率很高。

建议: 用 DMA 通道把 framebuffer 推到 SPI1:spi/dma 异步,CPU 只负责准备下一帧。M0+ 没有 cache,双缓冲要在 RAM 中预留 2 块 480*320*2 = 300 KB 区域(SRAM 264 KB 不够,需用 PSRAM 或压缩)。

折中:用 1 个 framebuffer + DMA 单缓冲,在 DMA 推流期间 CPU 准备下一帧,实现流水线。

✨ 值得保留的优良实践(5 项)

优点架构
单向依赖 + 静态库分层

app → ui → Drivers → SDK 的依赖方向完全单向,业务代码不会反向污染底层。--whole-archive 仅用于 minirtos(vector table 接管),--start-group 仅用于业务静态库,划分很清晰。

优点性能
32px 切片 + 脏矩形渲染

ui_tile_t 切片机制让全屏渲染可以分 15 个独立 tile 并行处理(虽然单核 M0+ 实际是串行),且每个控件的 draw 都会做 ui_rect_intersect 自裁剪。整页局部刷新(只刷抽屉 140px / 只刷按钮 220px)成为可能。

优点架构
边缘手势状态机的设计模式

edge_touch_down / edge_candidate / gesture_consumed 三态机区分"按下候选"、"消费中"、"释放",避免了一次边缘滑动被误识别为多次。

优点可移植
GBK 字符集贯穿

所有 .c 都加 -finput-charset=UTF-8 -fexec-charset=GBK,保证中文源码与运行时编码一致。嵌入式 GUI 项目最容易踩的"中文字符变 ?" 已规避。

优点架构
USB CDC 1ms 超时保护

PICO_STDIO_USB_STDOUT_TIMEOUT_US=1000 看似不起眼,但规避了"host 未开串口监视器时 printf 阻塞 500ms 卡死 RTOS 任务"的常见坑。应该作为项目标配。
