🔴 致命问题(必须修)

CRITui_render_tiles 在两个 .c 里同名不同签名

📁 ui_core.c:33 与 ui_tile.c:43

现象: 两个 .c 文件都定义了 ui_render_tiles,签名看起来一样但 typedef 不同:

// ui_core.h
typedef void (*ui_scene_draw_cb_t)(ui_tile_t *tile);
void ui_render_tiles(uint8_t, uint8_t, ui_scene_draw_cb_t);

// ui_tile.h
typedef void (*ui_tile_render_cb_t)(ui_tile_t *tile);
void ui_render_tiles(uint8_t, uint8_t, ui_tile_render_cb_t);

后果: 两个函数都进了目标文件,链接器会报 multiple definition of ui_render_tiles。即使暂时能过,运行时调到的版本也是不确定的(取决于链接顺序)。

修法: 二选一:

  • ui_tile.c 里的 ui_render_tiles 删掉(已被 ui_core.c 实现)
  • 或者 ui_tile.h 里的声明删掉(只留 ui_core.h 暴露)

CRITui_draw_string 依赖未声明的 Font5x7

📁 ui_draw.c:191
extern const uint8_t Font5x7[][5];

现象: 字符范围校验通过(' ' ~ '~' = 95 字符),索引安全,但 Font5x7 在 ui/ 下未定义(应该从 Drivers/chinese.c 来)。

后果: 如果 Drivers/chinese.c 没导出这个符号 → 链接报 undefined reference to Font5x7。建议先 nm build/ui/libuigeom.a | grep Font5x7 确认。

建议: 在 ui_draw.h 里也声明,让依赖关系显式化。

🟡 严重逻辑缺陷

BUG按钮触控语义和文档不一致(ui_btn)

📁 ui_btn.h:73 文档 vs ui_btn.c:112-146 实现

头文件注释写的是 "按下即触发 + 边沿防抖",但实际代码是 "松手才触发":

// 头文件说的:
@brief 处理触控输入（按下即触发 + 边沿防抖）

// ui_btn.c 实际写的 (line 119-126):
if (hit) {
    if (!btn->is_pressed) {
        btn->is_pressed = true;
        need_redraw = true;
    }
    return need_redraw;       // 按下不触发回调
}
// 松手才触发 (line 129-137):
if (btn->is_pressed && !is_touching) {
    if (now_tick - btn->last_tick <= 300) {
        btn->on_click(btn, btn->user_data);   // 回调在这
    }
}

后果: 调用方按文档预期写 "按下立即响应" 会扑空;长时间按住不松手,按钮看起来被锁死(状态没切换)。建议文档与实现对齐,或者明确文档为 "Click-on-release"。

BUGui_btn.c 注释里残留整段废弃实现

📁 ui_btn.c:75-111

旧版 ui_btn_process_touch 的完整逻辑(37 行)被注释掉保留,当前版本在 112-146 行。这段注释里的代码包含完全不同的语义(按下就触发回调 + 60ms 松手消抖),被废弃了。会让 reviewer/协作者困惑。

建议: 删掉,如果需要看历史走 git blame。

BUG下拉菜单 is_pressed 粘滞导致二次点击无效

📁 ui_dropdown.c:70-130

按下逻辑依赖 if (!dd->is_pressed) 守卫,但松手消抖要等 60ms:

// 按下 (line 77):
if (!dd->is_pressed) { dd->is_pressed = true; ... }

// 松手 (line 122-127):
if (dd->is_pressed) {
    if (now_tick - dd->last_tick >= 60) {
        dd->is_pressed = false;
    }
}

场景重现: 1) 用户按表头 → 菜单开,手指离开。2) is_pressed 还在等 60ms 复位。3) 用户 50ms 后再按表头 → is_pressed 还是 true,守卫失败 → 菜单无法关闭。

修法: 松手时立即复位 is_pressed = false,不挂 60ms(因为下拉菜单没有"按住-拖动"语义,延迟无意义)。

BUG下拉菜单"外部点击收起"只在按下时生效

📁 ui_dropdown.c:112-115
// 只在按下(is_touching=true)时检查外部点击
else {
    dd->is_open = false;
    return true;
}

后果: 用户在菜单外部按下又滑动出 → 不会触发关闭。只能"按下瞬间命中外部"才关闭。配合上一条的粘滞,菜单可能锁死在外。

建议: 考虑用专门的"模态屏蔽层"判定,或者只要当前触摸点不在总矩形内即认为外部点击。

BUG滑块拖拽结束条件不可达

📁 ui_slider.c:104-108
// 松手判定（60ms 滤波防抖）
if (slider->is_dragging) {
    if (now_tick - slider->last_tick >= 60) {
        slider->is_dragging = false;
        return true;
    }
}

问题: last_tick 在 hit/drag 分支(line 69)每帧都被刷成 now_tick。只要手指还在拖,这个差永远 < 60ms,松手后第一帧 last_tick 还是上一帧的 now_tick,差值大概率是 1 个 tick(<60)。

后果: 永远进不去松手分支,拖动结束的"重绘"事件不触发,直到下一次外部重绘。手感上看着不掉。

修法: 在 hit/drag 分支结束时(return value_changed; 之前)不要刷 last_tick;只在真正进入"非触摸"路径时记录一次。

BUG滚动视口的滚动判定阈值 6px 过小,误触发

📁 ui_scrollview.c:47
if (abs(delta_y) > 6) {
    sv->is_scrolling = true;
    ...
}

问题: 6px 阈值意味着轻微抖动就识别为滚动,正在点击的按钮、滑块、开关只要碰巧在视口内就会被识别为"开始滚动" — 后续 scroll_start_y 被覆盖,点击事件失活。

建议: 阈值提到 12~15px,或者干脆改成 "N 帧内位移持续增长才识别为滚动"。

🔵 一般代码质量

MINOR所有"控件"的 debounce_ms 字段从未被读取

📁 ui_btn.c:67、ui_switch.c:31、ui_slider.c(无此字段)

ui_btn_t::debounce_ms = 250、ui_switch_t::debounce_ms = 200 在初始化时设了,但代码里硬编码 60/300ms 阈值,这两个字段是死字段。

建议: 删字段,或者把硬编码的 60/300 改成 debounce_ms。

MINORUI_MIN/UI_MAX 宏不安全

📁 ui_geometry.c:3-4
#define UI_MIN(a, b) ((a) < (b) ? (a) : (b))
#define UI_MAX(a, b) ((a) > (b) ? (a) : (b))

这里 a / b 各被求值 2 次。当参数是带副作用的表达式(自增、函数调用)会爆。当前用法都是结构体字段访问,无副作用,但仍属脆弱代码。

建议: 改成 static inline 函数,顺便把类型固定为 int16_t(ui_geometry 内部都用 int16_t)。

MINORASCII 字符串测量宽度 ≠ 实际渲染宽度(按钮文字偏左)

📁 ui_btn.c:21-40 vs ui_draw.c:193-227
字号测量返回 (half_w)实际渲染 (char_w)差距
FONT_1686+33%
FONT_2010100
FONT_2412120

后果: FONT_16 字号下按钮文字测量比实际宽 33%,居中计算偏左,长文本会从按钮左边溢出。

建议: 用同一个 measure_string_width 函数给 ui_draw.c 也复用,统一宽度源。

全代码搜不到使用。

📁 ui_draw.c:191

现在 extern 藏在 .c 文件里,谁 include 了 ui_draw.h 都看不到这个依赖。挪到 ui_draw.h,或者至少在 ui_draw.h 里加注释说明依赖外部字体数组。

MINOR开关 (Switch) 缺少公共 API 设置 show_underline 风格的属性

📁 ui_btn.h:54

ui_btn_t::show_underline 字段存在但没有任何 setter API,外部无法打开。

MINOR所有控件的触控回调没有"重入安全"

📁 多处

回调里如果调用任何 ui_btn_set_xxx / ui_switch_set_state 修改自身状态,可能踩到当前正在遍历的状态机。建议在回调实现文档里加一行 "不要在回调内反调用 process_touch"。

MINORint total = tile->rect.w * tile->rect.h 潜在溢出

📁 ui_modal.c:145

两个 int16_t 相乘的结果赋给 int,理论上不会溢出(320×32=10240),但万一未来屏分辨率提到 1024×768 就溢出。改成 size_t 或者 (int32_t)tile->rect.w * tile->rect.h。

MINOR弹窗外暗化算法不准(& 0x7BEF)

📁 ui_modal.c:147
tile->buf[i] = (tile->buf[i] >> 1) & 0x7BEF;

右移 1 位=亮度减半,但 & 0x7BEF 又把 R/G/B 三色的 LSB 都清零了。复合效果不是简单的"变暗",而是 RGB 三通道都会"掉精度",看起来发灰、不自然。

建议: (tile->buf[i] >> 1) 即可,或者乘以 0.6((tile->buf[i] * 0x4D8B) >> 16)。

MINOR部分 API 缺少 NULL 检查

📁 ui_btn.c:213、ui_slider.c:206、ui_switch.c:47 等

绝大多数 setter 都做了 NULL 检查,但 ui_btn_set_color 等函数 NULL 检查后只是 return,没记日志也没断言。如果上游代码有 bug,setter 静默失败,后续渲染用错值会很难定位。

⚡ 性能热点

⚠ memset 每帧每切片调用一次

📁 ui_tile.c:21
memset(s_current_tile.buf, 0, UI_TILE_W * UI_TILE_H * sizeof(uint16_t));
// = memset(0, 20480 字节) 每切每帧

15 个切片 × 20KB = 300KB memset/帧。120MHz Cortex-M0+ 下大约 5~10ms 占用。

优化方向:

  • 用 DMA 做 memset(零拷贝 + 后台跑)
  • 改成只清"脏区域"(脏矩形 + ui_geometry 求并集)
  • 把 memset 放到 SPI 推流的等待窗口里做(并发掩盖)

⚠ ui_draw_fill_rect 每像素一次写

📁 ui_draw.c:48-73
for (y) for (x) tile->buf[ly * W + lx] = color;

320×480 全屏填充 = 153600 次写。填大色块会很慢,不如改成:

  • 整行写一次的 memset16(按 16-bit 颜色批量填)
  • DMA + 硬件加速(如果 LCD 控制器支持整块 fill 命令)
